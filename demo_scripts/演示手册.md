## 🎮 三、fault.sh 命令速查

| 命令 | 效果 | 演示场景 |
|------|------|---------|
| `bash fault.sh show` | 查看当前状态 | 开场展示"一切正常" |

| `bash fault.sh loss` | 📉 加丢包 50% | 网络质量下降 |


## 🛡 六、应急方案

### 情况 1：cloudflared 推送失败（`POST→HTTP 0`）
**现象**：日志出现 `WARN: Remote end closed connection`
**处理**：
- 不影响演示！说："网络有抖动，但有重试机制"
- 连续多周期都失败 → 切到"本地演示模式"（看 dashboard + 日志即可，跳过 A 同学部分）

### 情况 2：live_env 挂了
**现象**：日志不再更新
**处理**：
```bash
colima ssh -- bash -c "sudo pkill -9 -f live_env.py; sudo mn -c; sudo /tmp/start_live.sh"
```

### 情况 3：故障注入没效果
**现象**：注入后日志仍 `reachable=True`
**处理**：
- 等 20 秒（探测周期是 15 秒）
- 或用 `bash fault.sh show` 确认端口状态

### 情况 4：网络完全不通（A 同学远程）
**处理**：改局域网直连
```bash
# A 同学本地跑 assurance-agent，你直连他的局域网 IP
colima ssh -- bash -c "sudo pkill -f live_env.py"
# 用 A 同学的局域网 IP 重启（见下方"局域网直连"章节）
```

## 🔌 七、局域网直连（备选方案，最稳）

如果 A 同学**在现场**，强烈建议改用局域网直连（避开 cloudflared 抖动）：

```bash

# 3. 重启

# 传脚本 + 执行（同之前的流程）
```

- cloudflared：~55-64%
- 局域网直连：~99%

## 💬 九、老师可能问的问题

**Q1: 为什么每 15 秒采集一次？**
> 平衡实时性和开销。故障容忍度要求高的场景可以调到 5 秒，甚至 1 秒。

**Q2: 推送失败怎么办？**
> 有 3 层保护：① 5xx 自动重试 3 次（指数退避）② 409 状态机错特殊处理 ③ 失败不阻塞主流程，下个周期继续。

**Q3: 怎么知道是"链路断"而不是"主机挂了"？**
> 我们采集的不只是可达性，还有**端口状态**（down_ports）、**流表状态**（expected_flow_present）、**链路拓扑**。A 同学的诊断模块会综合这些信号判断根因。

**Q4: 这套系统能用于真实网络吗？**
> 可以。intensure 的采集层与控制器解耦，换成真实交换机（华为/思科）只需替换采集适配器，上层逻辑不变。

**Q5: 为什么不用大模型做诊断？**
> 确定性算法 + 知识库：可解释、低延迟（<100ms）、不消耗 token、无幻觉风险。未来可以接 LLM 做非典型故障的二次确认。
